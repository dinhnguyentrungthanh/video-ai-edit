# BiliFlow agent entry point

Before changing this repository, read these files in order:

1. `docs/SESSION_HANDOFF.md`
2. `docs/PROJECT_STATUS.md`
3. `README.md`
4. The latest entries in `CHANGELOG.md`

Then run `git status --short --branch` and `git log -8 --oneline --decorate`.
The handoff file records the active branch, the last verified real-video run, and the remaining work. Treat live dashboard state as ephemeral and verify it through the local API or artifacts before making claims.

## Project invariants

- BiliFlow is local-first. Do not introduce paid per-call APIs or models without an explicit user request.
- Keep every production model commercially usable and recorded in the license policy.
- Never modify or delete source videos. The only exceptions are two groups of user-triggered Control Center actions run after the user confirms the listed files in the dashboard dialog (the user chose this on 2026-10-05, `docs/DELETE_FLOW_PLAN.md`; group (1) on the PC or, since 2026-10-06, also through the Dashboard V2 phone mode on the home Wi-Fi or, by the user's choice on 2026-10-06, over Tailscale (`docs/DASHBOARD_V2_PHONE.md` section 8); group (2) on the PC only): (1) "Xóa video gốc" (formerly "Dọn video gốc", which moved the file to the Recycle Bin) permanently deletes an input video after its SHA-256 check. It applies only to a job whose active review revision has a completed export that passes its manifest check and was rendered from the current review decisions, or that the user marked "Bỏ qua (không xuất)" with a skip record that still matches the review. It then deletes that export's `…-reviewed.mp4.manifest.json` (directly in `output\`; the `.mp4` stays) and removes the job from BiliFlow. "Xóa video" removes a CANCELLED job (deleting its input video first, after the SHA-256 check, when it is still there) or a job whose source is gone (not archived; nothing in `output\` is touched). Removing a job deletes only: its rows in `state/control-center.sqlite3` (jobs, job_revisions, stages, artifacts, events, source_cleanups, source_archives, recycle_checks and its `<name>:<id>` settings; the watcher row of its file is reset, not deleted), its own report folders directly in `reports\jobs` (`<job_key>` or `<job_key>-run-*`, never a folder another job still names, one holding a `.biliflow-benchmark` marker, or a link) and its `logs\control-center\job-<id>-*.log`. Jobs of a golden set (`annotations\golden\*\segments.json`, by job id or SHA-256) are never deleted, and nothing is deleted while such a file cannot be read. No deletion log is kept (the user's choice). A job's source file is deleted first and its rows last, so an interrupted removal leaves a job without its source that "Dọn video mất gốc" removes again. Legacy rows of the old Recycle Bin cleanup still lock their job until it is removed: a Recycle Bin record found later is never written into that row; "Kiểm tra lại Thùng rác" only reads the bin and appends a `recycle_checks` row and a SOURCE_RECYCLE_VERIFIED or SOURCE_RECYCLE_STILL_UNVERIFIED event. (2) "Lưu trữ" and "Khôi phục bản xuất". For a job whose export passes the same checks as "Xóa video gốc", or that was skipped with a matching skip record, "Lưu trữ" renames the unchanged source from `<install>\input` into `<install>\archive\sources\<job_key>\` on the same volume, verifies its SHA-256 and then, for an exported job only, moves that job's current export (`output\…-reviewed.mp4` and its `.manifest.json`, directly in `output\`, never a subfolder or an alternate data stream) to the Windows Recycle Bin (never a permanent delete; refused when the bin capacity could be exceeded; if the export cannot be moved, the source is renamed back). Only an archive that succeeded keeps `archive-manifest.json` (or the next free numbered name) beside the archived file: it is prepared as a `.tmp` before the move and a rollback removes only that `.tmp`. "Khôi phục bản xuất" renames the archived file back to its original input path only when that path is free and the SHA-256 matches; an exported job then returns to review (READY_TO_EXPORT or WAITING_REVIEW) to be exported again, a skipped job stays SKIPPED. An interrupted archive or restore is settled at the next start without calling the Recycle Bin; a row whose files cannot be found or read is never settled on a guess: it keeps the job locked and logs an ERROR event. Neither action deletes or rewrites reports, review decisions, brand/studio memory, other outputs or anything in `archive\` (except its own unfinished `.tmp` manifest); in the database they only add `source_archives` rows (a latest PENDING, ARCHIVED or RESTORING row locks the job; never "repair" them), SOURCE_ARCHIVED and SOURCE_ARCHIVE_* events, the watcher row of the moved file and, on a restore, the job state above. Agents must never trigger these actions, call /api/source-cleanup, /api/job-delete, /api/source-archive*, /api/source-recycle-check, execute_cleanup, execute_delete, purge_job, delete_input_file, execute_archive, restore_archive, send_to_recycle_bin or send_export_to_recycle_bin on user files, or move or delete anything in `<install>\archive`. Tests may only delete, move or recycle temporary files they created under `E:\DungChung\BiliFlow\temp`; delete and archive tests use a temporary project root there (archive tests with a fake recycler), never `<install>\input`, `output`, `reports` or `archive`. The deleting functions refuse any project root other than the install root or a folder in its `temp`. The only real-bin test remains the opt-in BILIFLOW_TEST_RECYCLE_BIN=1 test (`tests.test_recycle_bin.RealRecycleBinTest`), which runs at most once and is then skipped because of its marker `temp\recycle-bin-test\ran-once.json`; there is no real-bin test for exports.
- Never auto-publish or upload.
- The video downloader (Dashboard V2 page `#downloads`, `/api/downloads…`) only downloads links the user pasted. Agents never add, resume or retry a download on the user's real Control Center and never POST to `/api/downloads*` there. A real-download check runs on a test Control Center started with a temporary project root under `E:\DungChung\BiliFlow\temp` and its own port, with links the user gave for that check; unit tests use the fake yt-dlp (`tests/fake_yt_dlp.py`). At the user's request on 2026-10-06, site-specific source resolution is allowed for user-pasted links: providers may read public page/player data to identify media, and a provider may use an ordinary browser in its own anonymous context when necessary. No DRM or paywall circumvention, CAPTCHA/anti-bot challenge bypass, or browser impersonation to bypass blocks. No user cookies, accounts or logins, with one exception: the source-account session the user creates themself (next item). yt-dlp and the anonymous providers never get any cookie or session. Provider requests and derived URLs must follow the downloader's network checks; signed URLs and tokens must not reach public API responses or logs. Branch `feat/download-source-providers` has the provider interface and one generic provider, `direct` (links whose path ends in .mp4/.m4v/.mov/.mkv/.webm/.ts or .m3u8; BiliFlow downloads them itself through `download_http.SafeHttp`); native page providers `player-hls` and `article-mp4` are registered (see docs/VIDEO_DOWNLOAD_PLAN.md section 4.12). The native `embedded-media` provider uses approved Playwright with headless Edge in a fresh temporary profile; all page requests are fulfilled through SafeHttp and the browser never downloads the media itself. Real provider hosts go only in the gitignored `config/download_providers.local.json`; it only switches providers of the code (`SITE_PROVIDERS`) on for exact host names and never names code or a command, and a host it lists for an id without a provider in the code is only recognized (its links keep the yt-dlp path, with a note), not supported. Automated provider tests use self-made clips and the local fixture server in `tests/source_fixtures.py`. Authorized real-source checks use only user-provided links and an isolated temporary root; never the real Control Center. The repository is public: no real video links, titles or non-example domains in code, tests, docs or commit messages. Downloading any tool or package needs the user's approval first.

A source configured with another adapter is still refused as described above (READER_UNSUPPORTED, LOGIN_UNSUPPORTED).
  - Sign-in. On the PC, the user picks a configured source in a combobox on the Tải video page and presses Đăng nhập. Only then does BiliFlow open a visible window of its own browser context, never a personal Edge or Chrome profile. The user signs in themself on the source's official site.
  - No passwords. BiliFlow has no password form and stores no password, in configuration or anywhere else. A sign-in counts only on evidence from the source's page or endpoint, never because the window closed. Cancelling or closing the window is never reported as success.
  - The session. BiliFlow keeps each source's session separately: only the context's authentication state, encrypted with Windows DPAPI for the current Windows user (never `CRYPTPROTECT_LOCAL_MACHINE`), in `state\source-accounts\<SID of the Windows account>\<source_id>\`. That account folder is private: its ACL grants only the Windows account running BiliFlow, SYSTEM and Administrators, with inheritance off. The account state in the database (`source_account_state`, keyed by that SID and the source id) is scoped the same way, and the SID comes only from the process token, never from a config or a request: another Windows account using the same install, before or after, has its own rows, generations and folder, starts as not connected, and never changes, invalidates or cleans up the first account's session. The vault refuses a folder or file whose ACL, owner or link status differs and never changes the rights of `state\` or the install folder. Only the cookies and origin storage of the source's own configured hosts are saved; whatever else the browser context holds is dropped. It uses the session only headless and only for that source's own hosts: to read the file list, get a download ticket and probe the file. Ngắt kết nối, pressed by the user, deletes only that source's own session files in that folder (`session-<generation>.bin` and their unfinished `.tmp`), after a path check; at start BiliFlow removes the same kinds of files of other generations and nothing else.
  - Session age. When a source has no real session check, BiliFlow asks for a new sign-in 3,600 seconds after the last successful one. Reaching that mark never stops a running file transfer.
  - Errors. Only an authentication error sends that source's tasks to WAITING_LOGIN, which holds no download slot. An expired ticket is refreshed first. Network, server, deleted-file and disk-space errors keep their own codes and never ask for a sign-in.
  - Still forbidden:
    - DRM or paywall circumvention: only what the signed-in account may already download;
    - CAPTCHA or anti-bot bypass: the user answers any challenge in the visible window;
    - changing the browser fingerprint;
    - importing cookies or sessions from a personal browser, an agent's browser or a Codex session.
  - Secrets. Cookies, session state, tickets, signed links and sign-in request bodies never reach logs, API responses (status included), Git or the public repository. Real hosts and login URLs go only in a Git-ignored local config; tracked files use `portal.example`, `tickets.example` and `files.example`.
  - Network. Every request of the authenticated browser keeps the downloader's network checks: public addresses only, DNS pinned at the connection, TLS checked, checked redirects, bounded reads and a deadline. Cookies go only to their own source's hosts. How (M2a): one route handler answers every request of the context with one checked exchange (https to a host of that source only, public addresses with DNS pinned at the connection, TLS checked, a byte limit and a deadline per request). Edge is never handed a 3xx (it would follow it outside the handler): a navigation gets a hop page to the checked target, other redirects are refused. What does not reach that handler (a shared worker's requests, worker sockets, Edge's own background traffic) ends at a black-hole proxy: launch flags (no QUIC, no DNS of its own) and a preference written into the fresh profile (no WebRTC UDP outside the proxy; Edge ignores the command-line switch for it) leave it no other way out. Edge keeps its sandbox. `SafeHttp` and the anonymous providers stay cookie-free.
    - One exception, M7 exception A (plan section 9.20): the user chose on 2026-10-10 to keep it. It is off unless a source's Git-ignored local config sets `page_script`. A hidden run that may ask for a ticket (never the sign-in window, never a list-only run) may load exactly one configured HTTPS script URL outside the source's hosts. Only a GET of resource type `script` to that exact host and path is answered. The page's own query (`_=<digits>`) is checked and never forwarded; the configured URL is fetched as written. It carries only Accept and User-Agent (no cookie, Authorization, Referer or Origin). A redirect is refused and no Set-Cookie reaches the page (only the content type and `no-store`). At most 4 such requests per run, 2 MiB and 20 seconds each, through the same checked client (public addresses, DNS pinned, TLS checked).
    - Every request the script makes in turn still goes through the route handler and is refused unless the rules above allow it. The script runs with the page's rights (it can read the page and its non-HttpOnly cookies): fetching it without cookies does not isolate its JavaScript, and this is not a sandbox. A wildcard host or a second script is never allowed, and A changes none of the other checks: the entry's request and method, the clicked control's submission, the ticket's provenance, the page's countdown and the exact file host. Real hosts and URLs live only in the local config.
    - The user's choice to keep A does not deploy it by itself: the main copy gets it only when the user asks to bring the branch in. The user asked on 2026-10-11 to bring the branch, with A, into the main copy.
  - Agents never:
    - press Đăng nhập or Ngắt kết nối, or POST to the source-account routes, on the user's real Control Center;
    - open, decrypt, copy or print a stored session;
    - sign in to a source themselves.
  - Tests use fakes and temporary roots under `E:\DungChung\BiliFlow\temp`. A real sign-in check runs only on a test Control Center, where the user signs in.

## Verification

- Run the focused tests for the files changed, then the full suite for detector, scheduler, review, or renderer changes.
- The standard full test command is `.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_*.py" -v`. The project test files use `unittest`; do not assume `pytest` is installed.
- Run `.\scripts\run.ps1 license-audit` when model manifests, dependencies, or license policy change.
- Real-video validation must report the exact job/revision and detector scope. A single-purpose scan never certifies skipped detector groups.
- Update `CHANGELOG.md`, `docs/PROJECT_STATUS.md`, and `docs/SESSION_HANDOFF.md` after a verified milestone.
