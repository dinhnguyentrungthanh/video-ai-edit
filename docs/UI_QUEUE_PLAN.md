## Vấn đề phản biện đã sửa trong kế hoạch
- **A/P3 FIFO: resume and retry**: Plan A gives a job a new queue_seq on Tiếp tục/Thử lại. The handoff spec (item 6) only sets queue time on JOB_QUEUED, EXPORT_QUEUED and rerun. With a new seq, a job paused by a graceful shutdown (JobScheduler.shutdown sets stop_mode=AFTER_STAGE, then _after_success sets PAUSED) drops to the back of the queue. So does a job that recover_interrupted() sets to INTERRUPTED_RECOVERABLE, and an accidental 'Dừng ngay'. → Have resume() and retry() keep the existing queue_seq and assign one only when it is NULL. Only start_job, rerun and queue_render (finalize) take a fresh seq. Ask the user to confirm this (question 1).
- **A/P3 FIFO: _select vs _execute race**: _select() reads a QUEUED job, then _execute() unconditionally runs update_job(state=definition.job_state). Suppose the user clicks pause, cancel, or Plan A's new 'remove from queue' (stop_after_stage → PAUSED) between those two calls. The worker then overwrites the PAUSED/CANCELLED state and runs the stage anyway. Plan A's new waiting-job pause depends on exactly this window. → Add JobStore.claim_queued(job_id, new_state, stage): `UPDATE jobs SET state=?,current_stage=?,error=NULL,updated_at=? WHERE id=? AND state='QUEUED' AND stop_mode IS NULL` and return rowcount==1. _execute() returns without running when the claim fails. Test it by patching _select to return a job that was paused in between.
- **A/P3 FIFO: rerun window and double click**: rerun() calls configure_and_queue, which sets state QUEUED and replaces the stages. Only afterwards does a second update_job clear active_queue_path and set QUEUED again. The worker can therefore start PREFLIGHT while the old revision is still active, and the second update can flip a running job back to QUEUED. rerun also takes no lock and has no state check: two quick 'Chạy lại' clicks create two pipeline keys (the same key within one second) and, with FIFO, two seqs. → Pass the reset fields (active_queue_path=None, active_revision=None, progress=0) into mark_queued so the clear happens in the same UPDATE, after replace_stages. Run rerun under _start_lock and refuse when the state is QUEUED or in IN_PROCESS_STATES. Clear render:{id} before queueing.
- **A/P3 import guard: manifest override**: Plan A still applies the manifest→COMPLETED override to WAITING_REVIEW and READY_TO_EXPORT jobs. A video that was exported, then rerun and re-reviewed, therefore flips back to COMPLETED on every restart, because import matches any manifest with the same source sha. A read-only check shows the risk is real: jobs 4, 37 and 38 are COMPLETED but no export exists for their active revision (review_export_paths(active queue) is missing). → Leave COMPLETED rows alone. Upgrade a READY/WAITING job to COMPLETED only when the manifest's output.path equals review_export_paths(root, active_queue)[1]. A new job, or one in NEEDS_METADATA or DISCOVERED, keeps today's rule. Add a job_import regression test for this case.
- **A/P3 recover_interrupted**: Confirmed: BUILDING_REVIEW is missing from the recovery list (job_store.py:512-515), so a crash during build_review leaves the job stuck forever. AI_AUDITING is listed but no stage ever sets it. → Keep Plan A's IN_PROCESS_STATES constant in job_store, include BUILDING_REVIEW, reuse it in scheduler.ACTIVE_STATES, and test it.
- **A/P3 migration**: _migrate() runs one executescript that already has the CREATE INDEX statements. If the new idx_jobs_queue(state,priority,queue_seq,id) were added to that script, an old DB would fail with 'no such column queue_seq' before the ALTER runs. → Create the queue index only after the PRAGMA table_info check and the ALTER TABLE ADD COLUMN step. Back up with sqlite3 Connection.backup to state/backups/ only when a column or table is actually added. SCHEMA_VERSION stays 1. Test against a copy of the live DB under temp/ui-plan/ (row counts unchanged, second open is a no-op, schema version 1).
- **A/P4 stage tabs + harness**: In the existing harness, jobs 44 and 45 are QUEUED with no queue_kind or queue_position. Under the new jobTab() they land in 'Đang chờ xử lý', so test_dashboard_behaviour_in_node_* (initial_order [45,44,46,47,48]) breaks silently, not as Plan A predicts. Plan A also wants the notice 'Đã xếp #id … (lượt p/n)' straight after Start, but POST /start returns the bare job row with no position. → Give the harness fixture queue_kind/queue_position and assign them in fakeFetch start. Build the notice from the load() that follows the POST, not from the POST response. Assert the new initial orders explicitly: waiting [46,47,48] and scan_queue in click order.
- **A/P4b + B/4 status payload**: Plan A reads review_summary through review_evidence.read_json_cached. Its LRU holds 16 entries (_JSON_CACHE_LIMIT=16), and the review page's evidence reads share it. A 3 s dashboard poll that parses queues (job 39's queue alone has 159 items and 294 advisory items) evicts the review page's working set. → Use Plan B's per-process count cache, keyed by (path, mtime_ns, size), that stores only {status, main_items, advisory_items, export_size_policy}. Compute it only for WAITING_REVIEW, READY_TO_EXPORT and SKIPPED.
- **A/P4b skip: guards and durability**: Plan A records the skip only as an event, and events are pruned at 10 000 rows. It does not refuse an active job, a queued or pending render, or a cleaned source. It does not say what finalize does on a SKIPPED job. → Adopt Plan B's settings key skip:{id}. Eligibility is decided from the stage table, not from the render:{id} setting, because render:{id} persists after completion and rerun only sets it to null. finalize() on a SKIPPED job raises 'Video đã được đánh dấu bỏ qua; bấm “Mở lại để xuất” trước.', so the dashboard and the review page behave the same and cleanup cannot race an export.
